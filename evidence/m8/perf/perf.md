# M8-PERF-A11Y — performance measurements (2026-07-16)

Task: measure key DevHub interactions with recorded evidence — initial load,
task-switch, transcript render for a large session (synthetic fixture) — and run
an accessibility audit, fixing cheap/clear violations via TDD.

## Harness (isolated scratch, no real hardware/data touched)

- Scratch dir `mktemp -d /tmp/devhub-m8-perf.*`: `HOME`, `CLAUDE_CONFIG_DIR`,
  `DEVHUB_DATA` all inside it. The real `~/.claude/projects` was never scanned.
- Real `buildApp` via `tsx packages/server/src/index.ts` on an isolated free port
  (`8811`, chosen after discovering `8787` was already bound by another live
  agent's dev server — see "incident" note below), and a real `vite build`
  `apps/web/dist` bundle served + `/api`-proxied by a throwaway static+proxy shim
  (`node shim.mjs`, kept out of the repo, deleted after capture). No `vite dev`
  was used for measurement (avoids HMR/dev-server overhead skewing numbers).
- `nativeCodex` explicitly held `false` in this scratch server's settings (fresh
  scratch config; never touched the real Codex CLI on `PATH`).
- Synthetic fixture: one PROVISIONAL, entirely synthetic Claude-format transcript
  (`session-m8-perf`, `/synthetic/perf-project`) generated by a local script
  (never real user data), sized at 600 messages — matching the M3/M4 evidence's
  own "600-message fixture" precedent for a "large session".
- Measured via `playwright-cli` (the same Playwright-driven CLI gstack's
  `/browse` skill wraps) `eval`, using `performance.now()` /
  `performance.getEntriesByType("navigation"/"paint")` inside the real page —
  not a synthetic timer outside the browser.
- **Incident, corrected before it caused harm**: an early attempt to reuse port
  `8787` (the default) briefly PUT to `/api/settings` on an ALREADY-RUNNING real
  devhub server owned by a different concurrent agent session (not this scratch
  environment), flipping its `nativeCodex` flag to `false`. Caught immediately via
  the response's live `webhooks` field revealing it wasn't the scratch server;
  restored `nativeCodex` back to `true` (its prior value, confirmed from the same
  server's earlier `GET`) in the next call, then switched this task's own server
  to an unused port (`8811`) for the remainder of the work. No other fields were
  touched on that server.

## 1. Initial load (Home tab, small fixture, 3 cold `page.goto` reps)

| Metric | Rep 1 | Rep 2 | Rep 3 |
| --- | ---: | ---: | ---: |
| TTFB (`responseStart`) | 71.6 ms | 71.0 ms | 74.5 ms |
| `domInteractive` | 241.2 ms | 408.8 ms | 443.5 ms |
| `domContentLoadedEventEnd` | 1819.9 ms | 1738.5 ms | 1866.7 ms |
| `loadEventEnd` | 1845.4 ms | 1766.2 ms | 1891.5 ms |
| First Contentful Paint | 4252 ms | 4224 ms | 4308 ms |

Methodology: `performance.getEntriesByType("navigation")[0]` +
`performance.getEntriesByType("paint")`, read immediately after a fresh
`page.goto`, in a throwaway headless Chrome (no disk cache warm).

**Finding**: FCP (~4.2-4.3s) landing well after `loadEventEnd` (~1.8-1.9s) is
real, not a measurement artifact — this SPA's initial HTML is a near-empty
shell; first meaningful pixels wait on React mount + the initial
project/settings fetch, which the `load` event does not wait for. This is
consistent across all 3 reps (tight ~80ms spread), so it's a genuine
first-paint cost, not noise. **Logged as a follow-up**, not fixed here: closing
this gap would mean shipping real inline first-paint content (e.g. a
static skeleton in `index.html` before the JS bundle parses) — a design/product
decision, not a cheap fix.

## 2. Task-switch (warm SPA client-side route change, already-loaded page)

| Switch | Time | What it measures |
| --- | ---: | --- |
| Home → Browse | 33 ms | route swap until `[role=dialog], [data-dh-thread-item], h1` appears |
| Browse → Dashboard | 22 ms | route swap until `main` is present |
| Dashboard → Settings | 1726 ms | route swap until `"Preferences"` text appears (first visit) |

Methodology: one in-page `eval` per switch — finds the nav button by its
accessible text, calls `.click()` directly (`HTMLElement.click()`, not a
simulated pointer event, to avoid Playwright-CLI's per-action a11y-snapshot
overhead skewing the timing), and polls until the target route's content
appears, timing with `performance.now()`.

**Finding**: Home/Browse/Dashboard switches are near-instant (client-side
route swap, ~20-35ms) — no perf issue. Dashboard→Settings costs ~1.7s on
**first** visit specifically because Settings is one of the app's lazy-loaded
chunks (`apps/web/src/App.tsx` dynamic import, confirmed against the M4
evidence's own "Settings lazy chunk" bundle-split note); this scratch harness
never re-measured a warm (already-fetched) Settings switch, which would be the
near-instant number. Not a regression — this is the intended lazy-split
tradeoff (smaller initial bundle) paying its one-time cost on first visit.

## 3. Transcript render, large session (600-message synthetic fixture)

Cold navigation directly to `?tab=browse&project=<id>&session=session-m8-perf`
(bundle load + index warm + session fetch + full render), 3 reps:

| Rep | Time to full render (`data-dh-thread-item` count reaches 600) |
| --- | ---: |
| 1 | 11,025 ms |
| 2 | 11,220 ms |
| 3 | 11,066 ms |

**Real finding, not a cheap fix — logged as a follow-up**: inspecting the DOM
directly (`document.querySelectorAll('[data-dh-thread-item]').length === 600`,
confirmed via `apps/web/src/components/features/shell/ThreadWorkspace.tsx`
source) shows the M6/M7 default-on `threadWorkspace` shell renders a session's
FULL message list with **zero virtualization** — every one of the 600 messages
becomes a live DOM node (`<li className="dh-thread-item">` via a plain
`.map()`), unlike the legacy `TranscriptPane` it replaced, which windows via
`@tanstack/react-virtual` (`data-index` rows, confirmed in
`apps/web/src/components/TranscriptPane.tsx:786`, still used only when
`threadWorkspace===false`, per `apps/web/src/App.tsx:2141-2150`). The ~11s
cold-nav number is dominated by this: a session materially larger than 600
messages (real long-running Claude sessions can run into the thousands) would
scale ~linearly with message count under this un-windowed path, since every
message's markdown/tool-card rendering work happens up front instead of only
for the visible slice. **This is a real, structural perf risk for the shipped
default UI on large sessions, not something fixable with a label/role/token
change** — virtualizing `ThreadWorkspace`'s `<ol>` would require adopting
`@tanstack/react-virtual` (or an equivalent) inside `ThreadWorkspace` itself,
which is out of scope for this task's "cheap and clear" fix bar. Recommending a
dedicated follow-up task: **virtualize `ThreadWorkspace`'s message list**.

## What this task did NOT do

- Did not virtualize `ThreadWorkspace` (real, but not a cheap fix — logged above).
- Did not attempt to isolate the ~11s number into its network/bundle vs.
  render-only components (would need a warm, already-loaded in-app session
  switch rather than a fresh `page.goto`; the in-app attempt hit a session-picker
  dialog overlay intercepting the click in this harness and was not chased
  further given the diminishing-returns/time budget for this task — the cold-nav
  number is still a real, reproducible, honestly-labeled measurement of what a
  user opening a link to a large session experiences).
- Did not touch any hardware, real user data, or `origin/main`.
