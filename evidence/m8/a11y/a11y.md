# M8-PERF-A11Y — accessibility audit (2026-07-16)

Task: run an accessibility audit (axe-core, via the same Playwright-driven
harness `/browse`/`playwright-cli` uses) over the main DevHub surfaces, record
findings, and fix the cheap/clear violations (labels, roles, contrast tokens)
via TDD — logging anything larger as a follow-up rather than silently passing.

## Harness

Same isolated scratch server + real `vite build` bundle + shim described in
`evidence/m8/perf/perf.md`. `axe-core@4.10.2` (real npm package, loaded via a
`<script>` tag from `cdn.jsdelivr.net` at audit time — this repo has no
`axe-core` devDependency, and adding a new devDependency wasn't warranted for a
one-off audit run) was injected into the live page and run via
`window.axe.run(document, { resultTypes: ["violations"] })`, i.e. it walks the
REAL rendered DOM of the real app, not a static snapshot.

Surfaces audited (`?tab=home|browse|dashboard|settings|inbox|ops|chat`, each a
fresh cold `page.goto` against the real app + real server): Home, Browse,
Dashboard, Settings, Inbox, Ops, Chat. Raw axe JSON output for every page,
before and after the fixes below, is under `evidence/m8/a11y/raw/`.

## Violations found and FIXED (TDD: failing test written first, then fixed)

| Violation (axe rule) | Surfaces | Fix | Test |
| --- | --- | --- | --- |
| `aria-required-children` (critical) — a `role="list"` (`TaskRail`'s `.dh-tasklist`) had a `role="presentation"` section-group `<li>` as its only effective child, which collapses out of the a11y tree and exposes the NESTED `role="list"` as an invalid grandchild | Home, Browse, Ops, Chat (every page with the M6 `TaskRail`) | `apps/web/src/components/features/shell/TaskRail.tsx`: `role="presentation"` → `role="listitem"` on the section-group `<li>` | `apps/web/src/components/features/shell/TaskRail.test.ts` (new case in the existing "open list" describe block) |
| `color-contrast` (serious) — `--dh-text-muted` (`#969696`) against the M6 rail's lightest surface `--dh-rail-active` (`#404040`) measured 3.5:1, below WCAG AA's 4.5:1 | Home, Browse, Ops, Chat | `apps/web/src/index.css`: `--dh-text-muted` `#969696` → `#b0b0b0` (4.78:1 against `--dh-rail-active`, verified ≥4.5:1 against every `dh-*` dark surface) | new `apps/web/src/lib/contrast-tokens.test.ts` (computes real WCAG contrast ratio from the actual CSS source, pins the fixed value) |
| `aria-progressbar-name` (serious) — `WorkModePanel`'s outcome progress bar had `aria-valuenow`/`min`/`max` but no accessible name (screen reader announced only "60% progress bar") | Home, Browse, Chat (wherever `WorkModePanel`/`WorkModeSurface` mounts) | `apps/web/src/components/features/shell/WorkModePanel.tsx`: added `aria-label={`${WORK_MODE_COPY.outcomeHeading}: ${task.outcome.summary}`}` | extended existing `WorkModePanel.test.ts` progress-bar case with a `toHaveAccessibleName` assertion |
| `aria-input-field-name` (serious) — the Browse-column `role="listbox"` containers (shared `useListKeyboardNav` hook; sets `role: "listbox"` with no way to carry a label) had no accessible name | Browse | `apps/web/src/components/ProjectsPane.tsx` / `SessionsPane.tsx`: added `aria-label="Projects"` / `aria-label="Sessions"` on each listbox container | new `apps/web/src/components/listbox-accessible-names.test.ts` (cheap source-static check, same pattern as the existing `App.preservation-routes.test.ts` — a full `<ProjectsPane/>`/`<SessionsPane/>` DOM mount would need the whole session/project data + callback surface mocked with no existing render harness) |
| `aria-prohibited-attr` (serious) — `DashboardSkeleton`/`TranscriptSkeleton`/`ListSkeleton` had `aria-label` on a bare `<div>` with no role (ARIA disallows `aria-label` on an element with no corresponding role) | Dashboard (flagged); Browse/Chat (same pattern, fixed preventively — same rule would have hit them the moment axe covered their loading states) | `apps/web/src/components/Skeleton.tsx`: added `role="status"` to all three skeleton containers | new `apps/web/src/components/Skeleton.test.ts` (jsdom + RTL, asserts `getByRole("status", { name: ... })`) |
| `heading-order` (moderate) — `InspectorDock`'s persistent Environment region used `<h3>` with no `<h2>` anywhere earlier in the dock's own subtree (invalid level-2 jump) | Browse, Chat | `apps/web/src/components/features/inspectors/InspectorDock.tsx`: `<h3 className="dh-inspector-env-heading">` → `<h2>` (matches the sibling "disclosure" variant's own top-level `<h2>` at the same structural depth) | extended existing `InspectorDock.test.ts` Environment-region case |

Confirmed fixed by re-running the exact same axe script against the rebuilt

## Violations found and NOT fixed — logged as follow-ups (too large for "cheap")

| Violation | Surface | Why not fixed here |
| --- | --- | --- |
| `nested-interactive` (serious) — `SessionsPane`'s session row (`role="option"` per the shared `useListKeyboardNav` listbox pattern) contains multiple focusable descendants (select checkbox, pin button, rename/delete actions) | Browse | `role="option"` elements are meant to be leaf, selectable items per the ARIA listbox pattern; multiple real interactive affordances per row is a genuine interaction-model tradeoff (not a label/role/token typo) shared by both `ProjectsPane` and `SessionsPane`. Fixing it means redesigning how per-row actions coexist with the option/listbox pattern (e.g. moving actions to a separate always-visible action bar, or switching the whole list to a different ARIA pattern like `grid`/`treegrid`) — a real UX/architecture decision, not a cheap fix. **Follow-up**: redesign session/project row actions to not nest interactive controls inside `role="option"`. |
| `color-contrast` (serious) — a SEPARATE, unrelated token pair: `--text-dim`/`--text-muted`-family zinc-500 text (`#71717b`/`#71717a`) against `--panel` (`#18181b`), measured 3.67:1, on the M6 secondary-nav / tab-strip controls (`.capitalize.px-3.py-1` / `.px-3.capitalize.hover:text-zinc-300`) | Browse, Ops, Chat (dark theme, confirmed after forcing `data-theme="dark"`) | Distinct from the `--dh-text-muted`/`--dh-rail-active` pair fixed above (different tokens, different surfaces, 19-26 nodes per page) — this is a broader design-system-wide token audit (the same zinc-500 family is used across many components), not a single isolated swap. Bumping it blind risks a much larger, unreviewed visual diff. **Follow-up**: audit `--text-dim`/zinc-500 usage against `--panel`/`--bg` across the M6 secondary-nav family specifically and pick a compliant replacement with visual review. |
| **Light theme, wholesale** (multiple `color-contrast` failures, e.g. `#efbfa9` on `#f9ebe6` at 1.42:1) | Every surface, but ONLY when `data-theme="light"` resolves (confirmed this headless Chrome's default `prefers-color-scheme` is light, so the app's default `theme: "system"` setting genuinely renders the light palette here) | `apps/web/src/index.css`'s own comment marks the light palette explicitly "inert until a component reads these tokens... Not wired to any UI yet (groundwork only)... light is a supported theme audited separately in M8." This audit ran primarily under dark (the shipped default look and the "fidelity authority" per the same comment) and only incidentally discovered the light palette is reachable (via `system` + a light OS preference) and has real, serious contrast bugs of its own. A full light-theme contrast pass is exactly the "separately in M8" scope the comment anticipates and is too large to fold into this task's cheap-fix bar. **Follow-up**: run this same axe pass with `data-theme` forced to `"light"` across all seven surfaces and fix the light palette's contrast tokens. |
